# แผนส่งมอบ: เอกสารรายสถานประกอบการและหนังสือตอบรับร่วมกัน

## สถานะและวิธีใช้

เอกสารนี้เป็นแผนสำหรับ AI coding agent ที่จะรับงานต่อใน repository นี้ ไม่ใช่หลักฐานว่างานถูกพัฒนาแล้ว และไม่ให้อำนาจ commit, push, deploy, ลบข้อมูลจริง หรือแก้เอกสารราชการที่ออกไปแล้วโดยไม่มีประวัติ

**เริ่มงานเมื่อผู้ใช้สั่งให้ลงมือพัฒนาแผนนี้** อ่าน `AGENTS.md`, `docs/fix-ui/UI-CONTRACT.md`, skill ที่เกี่ยวข้อง และตรวจ `git status` ก่อนแก้ไฟล์ทุกครั้ง รักษาการเปลี่ยนแปลงที่มีอยู่ เพราะ ณ วันที่เขียนแผน worktree มีการแก้ไขหลายไฟล์ รวมทั้ง schema และ workflow เอกสาร

แผนเก่า `docs/request-letter-generation-implementation-plan.md` เป็นบริบททางประวัติศาสตร์ของการสร้าง PDF รายคน มีข้อจำกัดว่าไม่เปลี่ยน workflow หนังสือตอบรับและไม่ทำหนังสือส่งตัว ซึ่งไม่ตรงกับคำขอปัจจุบัน ให้ยึดคำขอล่าสุดและแผนนี้เมื่อข้อกำหนดขัดกัน แต่ตรวจ implementation จริงใหม่ก่อนลงมือ

## Prompt ส่งมอบให้ AI agent

```text
ดำเนินงานตาม docs/company-document-batches-implementation-plan.md ให้ครบทุกเป้าหมายที่ตรวจรับได้

เริ่มด้วย Phase 0 และตรวจ worktree/ฐานข้อมูลจริงก่อนแก้ schema หรือข้อมูล รักษาไฟล์ที่มีอยู่ทั้งหมด
ทำ Phase 1–5 ตามลำดับ โดยแต่ละ Phase ต้องผ่าน completion gate และ acceptance scenario ที่เกี่ยวข้อง
แก้ทั้ง backend, สิทธิ์เข้าถึง, migration, UI เจ้าหน้าที่/นักศึกษา และ tests ที่จำเป็น ไม่หยุดที่หน้าตา UI
หากพบข้อมูลจริงที่ขัดกับข้อสมมุติหรือจำเป็นต้องเปลี่ยนกฎเอกสาร ให้รายงานหลักฐานและถามเฉพาะจุดนั้น
เมื่อส่งมอบ ให้สรุปไฟล์ที่เปลี่ยน หลักฐานทดสอบ สิ่งที่ยังไม่ผ่าน และผลต่อข้อมูลเดิมอย่างตรงไปตรงมา
```

## เป้าหมายที่ตรวจรับได้

1. ใน `/staff/cooperative-cycles/:cycleId/applications` เจ้าหน้าที่เห็นบริษัททั้งรอบสหกิจพร้อมสถานะเอกสารที่ถูกต้อง ไม่ถูกตัดตาม pagination ของคำร้องรายคน
2. เปิดรายละเอียดบริษัทได้ เห็นข้อมูลบริษัท นักศึกษาและตำแหน่ง ช่วงเวลาฝึก เอกสารทุกฉบับ สถานะ และประวัติ
3. Modal ออกหนังสือขอความอนุเคราะห์รวมเสนอเลขที่หนังสืออัตโนมัติตามปี และเจ้าหน้าที่แก้เลขก่อนออกได้ โดย server ป้องกันเลขซ้ำและบันทึกเลขจริงที่อยู่บน PDF
4. สมาชิกในหนังสือขอความอนุเคราะห์ฉบับเดียวกันได้รับการแจ้งเตือน และแต่ละคนดาวน์โหลด PDF ฉบับเดียวกันได้จากสิทธิ์ของตน
5. สมาชิกคนใดคนหนึ่งอัปโหลดหนังสือตอบรับแทนชุดได้ เมื่อส่งแล้วสมาชิกคนอื่นส่งซ้ำไม่ได้ แต่ดูสถานะและดาวน์โหลดไฟล์เดียวกันได้
6. เจ้าหน้าที่อนุมัติหรือส่งกลับหนังสือตอบรับหนึ่งครั้งแล้วส่งผลต่อสมาชิก **เฉพาะฉบับนั้น** ทั้งหมด พร้อมแจ้งเตือนทุกคน
7. ผู้สมัครช้าของบริษัทเดียวกันที่อยู่คนละหนังสือยังคงเป็นอีกชุด ไม่ถูกอัปเดตหรือแจ้งเตือนตามฉบับก่อน
8. หนังสือส่งตัวอ้างอิงหนังสือขอความอนุเคราะห์ฉบับที่ถูกต้องและออกให้รายชื่อชุดเดิมหลังยืนยันครบ

กรณีเกิน 6 คนต่อหนังสือขอความอนุเคราะห์ยังพักไว้ตามคำสั่งเดิม; อย่าขยาย PDF เป็นหลายหน้าในงานนี้

## กติกาโดเมนที่ให้ใช้ระหว่างพัฒนา

- **หนึ่งชุด = `RequestLetterVersion` หนึ่งฉบับ** พร้อม participant snapshot ไม่ใช่ทุกคำร้องของบริษัทตลอดทั้งรอบ บริษัทเดียวกันอาจมีหลายฉบับเพราะผู้สมัครช้า
- หนังสือขอความอนุเคราะห์, หนังสือตอบรับ และหนังสือส่งตัวที่เกี่ยวกันต้องอ้างอิง ID ฉบับเดียวกัน ไม่จับคู่จากชื่อบริษัทอย่างเดียว
- สมาชิกคนใดก็เป็นผู้อัปโหลดหนังสือตอบรับฉบับแรกหรือฉบับแก้ไขได้ ไม่กำหนดตัวแทนล่วงหน้า เก็บ ID ผู้ส่งจริงเพื่อ audit
- เมื่อมีหนังสือตอบรับ `UPLOADED/UNDER_REVIEW` สมาชิกทุกคนเห็นสถานะรอตรวจ และทุกคนถูกปิดสิทธิ์อัปโหลดเพิ่ม จนกว่าเจ้าหน้าที่ส่งกลับแก้ไข
- เมื่อ `RETURNED_FOR_REVISION` สมาชิกคนใดก็อัปโหลด version ใหม่ได้; version เก่าคงอยู่ในประวัติและไม่ใช่ไฟล์ปัจจุบัน
- เมื่อ `APPROVED` สมาชิกทุกคนเป็น `PLACEMENT_CONFIRMED`, application เป็น `CONFIRMED`, ดาวน์โหลดไฟล์เดียวกัน และอัปโหลดเพิ่มไม่ได้
- การอัปโหลด/อนุมัติ/ส่งกลับต้องตรวจสถานะสมาชิกทั้งชุดและป้องกันการกดพร้อมกันใน transaction; UI ซ่อนปุ่มอย่างเดียวไม่เพียงพอ
- กรณีคำร้องเก่าที่ไม่ได้อยู่ในฉบับรวม ให้ workflow รายคนยังทำงานได้
- หากสมาชิกคนใดถูกยกเลิก/ปฏิเสธหรือเปลี่ยนบริษัทหลังออกฉบับรวม ห้ามอนุมัติทั้งชุดแบบเงียบ ๆ; แสดงข้อขัดแย้งให้เจ้าหน้าที่จัดการฉบับอ้างอิงก่อน

## แบบข้อมูลที่แนะนำ (ยืนยันกับ schema จริงก่อน migration)

ใช้ `RequestLetterVersion` เป็นตัวกลางที่มีอยู่แล้ว แทนการสร้างแนวคิด “บริษัทหนึ่งเอกสารเดียว” ซ้ำอีกชุด

1. เพิ่ม `requestLetterVersionId` แบบ nullable ให้ `RequestDocument` เพื่อระบุว่าหนังสือตอบรับนี้เป็นของฉบับรวมใด; ค่า `null` หมายถึง workflow รายคนเดิม
2. คง `cooperativeRequestId` ของ `RequestDocument` ไว้เป็นคำร้องของ **ผู้ที่อัปโหลดจริง**; ไม่ใช้ field นี้เป็นตัวบอกสิทธิ์ดาวน์โหลดของทั้งชุด
3. เพิ่ม `groupVersion` หรือเลข revision ระดับ `requestLetterVersionId`, มี unique constraint `(requestLetterVersionId, groupVersion)` เพื่อเรียงประวัติแม้คนละคนเป็นผู้ส่งฉบับแก้ไข; `version` รายคำร้องเดิมยังใช้กับข้อมูลเก่าได้
4. สร้าง relation/index สำหรับ query เอกสารตอบรับจากฉบับรวมและ participant; ตรวจ existing rows และ migration ของโครงสร้างกลุ่มที่ยังไม่อยู่ใน migration history ก่อนใช้ `migrate dev` หรือ `db push` ห้าม reset/ทิ้งข้อมูล
5. พิจารณาเลขที่หนังสือเป็นทะเบียนกลางสำหรับทั้งหนังสือขอความอนุเคราะห์และหนังสือส่งตัว: `(ปี พ.ศ., เลขที่ normalized)` ต้อง unique ฝั่ง DB เพราะเลข manual ที่แก้ได้อาจชนกับเลข auto หรือคนอีกคนออกพร้อมกัน บันทึกสถานะเลขที่จอง/ออก/ยกเลิกเพื่อไม่ให้เลขที่เคยใช้ถูกนำกลับมาใช้เงียบ ๆ

ถ้าการขยาย `RequestDocument` ทำให้ constraint เดิมขัดกับ revision ข้ามผู้ส่ง ให้ปรับ versioning เฉพาะส่วนจำเป็นตามข้อมูลจริง ไม่ย้ายเอกสารเก่าไป schema ใหม่โดยไม่มีแผนตรวจย้อนหลัง

## ลำดับดำเนินงานและ completion gate

### Phase 0 — ตรวจข้อมูลจริงและรักษาความเข้ากันได้

- ตรวจ schema, migration status และตัวอย่างข้อมูลแบบ read-only: ฉบับรายคน, ฉบับรวม, คำร้องที่มี `letterFilePath` แต่ไม่มี version, รายชื่อที่มี active letter ซ้อนกัน, เลขหนังสือซ้ำ/รูปแบบไม่สม่ำเสมอ
- ระบุวิธีจัดการ legacy ที่ชัด: การสร้างฉบับรวมใหม่ต้องไม่ปล่อย active version รายคนอีกฉบับให้ endpoint เลือก PDF ผิด; หากต้องแทนที่ ให้ supersede รายการที่เกี่ยวข้องครบทุกคนใน transaction และเก็บประวัติ
- ตรวจคลังไฟล์ว่าตัวอย่างที่ใช้ยังมีไฟล์จริง โดยไม่เปิดเผยข้อมูลนักศึกษาในผลรายงาน
- **ผ่านเมื่อ:** มีรายการความขัดแย้งพร้อมจำนวนและกฎ migration/reconciliation ที่ไม่ทำข้อมูลเดิมหาย หากพบข้อมูลที่ต้องตัดสินใจเชิงธุรกิจ ให้หยุดเฉพาะจุดที่ขึ้นกับคำตอบและทำงานอิสระส่วนอื่นต่อ

### Phase 1 — เลขที่หนังสือที่แก้ได้

- เพิ่ม API เสนอเลขตามวันที่/ปีเพื่อกรอกใน modal; ค่านี้เป็นเพียงคำแนะนำ ไม่ถือว่าจองเลข
- ช่องเลขที่หนังสือใน modal แสดงค่าที่เสนอและแก้ได้; เปลี่ยนวันที่ข้ามปีแล้วต้องขอคำแนะนำปีใหม่ เว้นแต่เจ้าหน้าที่แก้เลขเอง
- ส่ง mode `AUTO`/`MANUAL` ให้ API ชัดเจน: `AUTO` ให้ server จัดสรรเลขล่าสุดเมื่อยืนยันและละค่าที่ client ส่งมา; `MANUAL` ใช้เลขที่เจ้าหน้าที่กรอกหลัง normalize/validate
- ตรวจซ้ำในทะเบียนเดียวกันทั้งสองชนิดหนังสือ รวมเลขไทย/เลขอารบิกและ prefix ที่อาจพิมพ์มา; เมื่อชนให้ 409 พร้อมข้อความแก้ไขได้ ไม่สร้าง PDF/เปลี่ยนสถานะ
- บันทึกเลขที่ได้จริงใน version และ render PDF ด้วยเลขเดียวกัน; ตอบกลับเลขจริงให้ UI แสดงหลังสำเร็จ การแก้เลขหลังออกต้องเป็นฉบับใหม่ที่มีประวัติ ไม่แก้ metadata/PDF เดิมอย่างเดียว
- **ผ่านเมื่อ:** auto สอง request พร้อมกันได้เลขต่างกัน, manual ชน auto ถูกปฏิเสธ, เปลี่ยนปีเริ่มลำดับตามปี, PDF/ฐานข้อมูล/หน้ารายละเอียดแสดงเลขเดียวกัน, failure ไม่ทำให้เลขที่เคยจองถูกนำไปออกซ้ำ

### Phase 2 — รายการบริษัทและหน้ารายละเอียด

- เพิ่ม API สรุปบริษัทจากคำร้อง **ทั้งรอบ** โดย group ด้วย `companyId` และ `cycleId`; แยกชุดเอกสารภายในบริษัทด้วย recipient/ที่อยู่ออกหนังสือ/ฉบับ ไม่ใช้ `companyName` เป็น identity
- แบ่งหน้าที่ระดับบริษัทสำหรับแท็บสถานประกอบการ ค้นหา/กรองแล้ว reset หน้า 1; แท็บนักศึกษายังใช้ API รายคนเดิม
- เพิ่มคอลัมน์ `เอกสาร` ใน UTable บริษัท: แสดงจำนวนหนังสือขอความอนุเคราะห์, สถานะหนังสือตอบรับล่าสุด และทางเปิดหน้ารายละเอียด โดย badge มีข้อความชัดเจน
- สร้างหน้า `/staff/cooperative-cycles/:cycleId/applications/companies/:companyId` พร้อม API ตรวจ role+cycle+company: ข้อมูลติดต่อ/ที่อยู่บริษัท, นักศึกษาในรอบนี้พร้อมตำแหน่งและสถานะ, กำหนดฝึกของรอบ, รายการหนังสือทุกฉบับพร้อมเลขที่/วันที่/รายชื่อ snapshot, หนังสือตอบรับ, หนังสือส่งตัว, ประวัติ และ action ที่ใช้ได้จริง
- แสดงวันฝึกว่าเป็น **กำหนดการของรอบสหกิจ** จนกว่าจะมีข้อมูลจริงรายคน อย่าสร้างวันรายคนจากการคาดเดา
- ตรวจ UI ตาม `docs/fix-ui/UI-CONTRACT.md` และ `/dev/ui`; ตารางต้องใช้ UTable, มีสถานะ loading/empty/error และ desktop/narrow viewport
- **ผ่านเมื่อ:** บริษัทที่มีนักศึกษากระจายข้ามหน้าของตารางรายคนยังมีจำนวนถูกต้อง; บริษัทชื่อเหมือนกันแต่ `companyId` ต่างกันไม่ปน; ฉบับที่ออกให้นักศึกษาสมัครช้าปรากฏแยกจากฉบับแรก

### Phase 3 — หนังสือตอบรับหนึ่งไฟล์ต่อหนึ่งฉบับรวม

- อัปเดต student/context และ applications API ให้คืน active `RequestLetterVersion` และหนังสือตอบรับปัจจุบันที่สัมพันธ์กับสมาชิกคนนั้น แยกจากเอกสาร legacy รายคน
- เปลี่ยน POST อัปโหลดให้ resolve ฉบับจาก membership ของผู้ใช้ฝั่ง server; ถ้ามีหลายฉบับหรือ legacy ต้องเลือกฉบับที่แน่ชัด ห้ามอาศัย company name จาก client
- ตรวจสิทธิ์, สถานะสมาชิกทั้งชุด, MIME/ขนาด/ลายเซ็นไฟล์ และ lock ฉบับรวมใน transaction ก่อนสร้าง record; หากมีคนแรกส่งแล้ว request ที่สองต้องได้ 409 แม้กดพร้อมกัน
- เขียนไฟล์แบบปลอดภัยและลบไฟล์ใหม่หาก transaction ล้ม; เก็บ uploader, เวลา, revision, status, file metadata; เก็บประวัติฉบับเก่า
- หน้า student แสดงชื่อผู้ส่งหรือข้อความ “สมาชิกในชุดส่งแล้ว”, สถานะ, วันที่, ปุ่มดาวน์โหลด; ปุ่มอัปโหลดของทุกคนปิดเมื่อรอตรวจหรืออนุมัติ และเปิดอีกครั้งเมื่อถูกส่งกลับ
- ปรับ download endpoint ให้สมาชิกของฉบับนั้นทุกคนเข้าถึงหนังสือตอบรับเดียวกันได้ แต่คนนอกชุด/คนละรอบไม่ได้
- **ผ่านเมื่อ:** สมาชิก A ส่งแล้ว B เห็นไฟล์และส่งไม่ได้; POST พร้อมกันจาก A/B สำเร็จเพียงหนึ่งรายการ; บุคคลนอกชุดดาวน์โหลดไม่ได้; สมาชิกคนละฉบับในบริษัทเดียวกันยังส่งของฉบับตัวเองได้

### Phase 4 — ตรวจอนุมัติและส่งกลับพร้อมกันทั้งชุด

- เพิ่ม action ระดับฉบับรวมในหน้ารายละเอียดบริษัท/API staff; ปุ่มรายคนเดิมให้ใช้เฉพาะเอกสาร legacy หรือ route ผ่าน logic เดียวกันเมื่อมี group ID
- `อนุมัติ`: lock ฉบับ, ตรวจ latest response เป็น `UPLOADED/UNDER_REVIEW`, เปลี่ยนเป็น `APPROVED`, อัปเดตทุก `CooperativeRequest` เป็น `PLACEMENT_CONFIRMED` และทุก `CompanyApplication` เป็น `CONFIRMED` ใน transaction เดียว, แจ้งทุกคน
- `ส่งกลับแก้ไข`: ต้องมีหมายเหตุ; latest response เป็น `RETURNED_FOR_REVISION`, ทุก request ในชุดเป็นสถานะเดียวกันและเห็นหมายเหตุเดียวกัน, แจ้งทุกคน; สมาชิกคนใดอัปโหลด revision ใหม่ได้
- ห้าม retry action แล้วส่ง notification หรือสร้าง revision ซ้ำ; ไม่แตะนักศึกษาชุดอื่นในบริษัทเดียวกัน
- ตรวจ API หนังสือส่งตัวให้ resolve request letter version ที่ถูกต้องและ participant snapshot ชุดเดิม; ทุกคนหลังอนุมัติครบต้องดาวน์โหลด sending PDF เดียวกันได้
- **ผ่านเมื่อ:** อนุมัติ/ส่งกลับครั้งเดียวอัปเดตสมาชิกครบ N คนและไม่มีคนนอกชุดเปลี่ยน; หน้าของทุกคนแสดงสถานะ/ไฟล์ตรงกัน; หนังสือส่งตัวออกได้หลังอนุมัติ

### Phase 5 — แจ้งเตือนตรงฉบับและตรวจทั้งระบบ

- แจ้งสมาชิกทุกคนเมื่อออกหนังสือ, มีคนส่งหนังสือตอบรับ, ส่งกลับ, อนุมัติ และออกหนังสือส่งตัวตามเหตุการณ์ที่ควรรับรู้ โดยมีลิงก์ตรงสู่รายละเอียดหรือ download endpoint ที่ตรวจ membership
- ออกแบบให้ notification ล้มเหลวไม่ทำไฟล์/สถานะย้อนกลับแบบไม่ตั้งใจ แต่มีหลักฐานและ retry ที่ตรวจสอบได้; อย่าส่งเฉพาะผู้ upload
- ทดสอบ API permission, state transitions, concurrency, legacy, late applicant, duplicate number, PDF เดียวกัน, สถานะใน staff/student และ browser console
- รัน focused tests → `pnpm exec prisma validate` หลัง schema → `pnpm typecheck` → `pnpm build` → `git diff --check`; หลังแก้ UI ต้องตรวจ authenticated desktop ประมาณ 1280px และ narrow ประมาณ 390px เทียบ `/dev/ui`; หากเข้าไม่ได้ ให้รายงานว่า visual gate ยังไม่ผ่าน
- **ผ่านเมื่อ:** ทุกข้อใน “เป้าหมายที่ตรวจรับได้” มีหลักฐานทดสอบ และไม่มีการอ้างว่าแผนเสร็จเพียงเพราะ build ผ่าน

## Acceptance scenarios ที่ต้องมีในการทดสอบ

1. บริษัท A รอบเดียวกันมี 3 คนในฉบับ 1; ทั้งสามได้รับลิงก์และดาวน์โหลด PDF hash เดียวกัน
2. บริษัท A มีผู้สมัครช้าอีก 1 คนในฉบับ 2; การส่ง/อนุมัติฉบับ 1 ไม่เปลี่ยนฉบับ 2
3. บริษัทสองแห่งชื่อแสดงเหมือนกันแต่ `companyId` ต่างกัน ไม่ปนในหน้ารายละเอียด
4. คน A และ B จากฉบับเดียวกันอัปโหลดในเวลาใกล้กัน; มี response version ปัจจุบันเพียงหนึ่งและอีกคำขอได้ 409
5. เมื่อ A ส่ง B เห็นสถานะรอตรวจ ดาวน์โหลดได้ และส่งซ้ำไม่ได้; คน C นอกชุดเข้าถึงไฟล์ไม่ได้
6. เจ้าหน้าที่ส่งกลับพร้อมหมายเหตุ; ทั้งชุดเห็นหมายเหตุและคนใดก็ส่ง revision ใหม่ได้ ขณะที่ไฟล์เดิมยังอยู่ในประวัติ
7. เจ้าหน้าที่อนุมัติ; request/application ทุกคนในฉบับเปลี่ยนสถานะ, notification ครบ, ส่งตัวอ้างอิงเลข/วันที่ของฉบับถูกต้อง
8. คำร้องเก่ารายคนยังอัปโหลด ตรวจ และดาวน์โหลดได้; คำร้องที่ไม่มี version แต่มี legacy path ไม่ถูกจับเข้า group โดยไม่ตรวจ
9. เลขแนะนำถูกแก้ก่อนออก; เลขซ้ำถูกปฏิเสธ; เลข auto ของการออกพร้อมกันไม่ซ้ำ; วันที่เปลี่ยนปีใช้ลำดับปีใหม่
10. รายการบริษัทและคอลัมน์เอกสารนับครบแม้คำร้องมากกว่า page size; หน้า detail แสดงช่วงเวลาระดับรอบตามจริง

## ข้อสมมุติและคำถามที่ต้องยืนยันเฉพาะเมื่อกระทบผลลัพธ์

- **ค่าตั้งต้นของแผน:** “แก้เลขได้” หมายถึงแก้ใน modal **ก่อนออก**; หลังออกให้สร้างฉบับใหม่และเก็บฉบับเดิม หากผู้ใช้ต้องการแก้เลขฉบับที่ประกาศใช้แล้วโดยไม่ออกใหม่ ต้องขอแนวทางงานสารบรรณก่อน
- **ค่าตั้งต้นของแผน:** หนังสือตอบรับหนึ่งไฟล์ครอบคลุมทุกคนใน RequestLetterVersion นั้น แม้บริษัทเดียวกันมีหลายฉบับ; หากบริษัทส่งตอบรับรวมข้ามหลายฉบับ ต้องออกแบบความสัมพันธ์ใหม่ก่อนลงมือ
- **ค่าตั้งต้นของแผน:** สมาชิกคนใดก็ส่งฉบับแก้ไขหลังถูกส่งกลับได้ เพราะผู้ใช้ระบุว่าไม่กำหนดผู้ส่งล่วงหน้า
- **ต้องตรวจข้อมูลจริง:** มีเลขสารบรรณภายนอกระบบหรือรูปแบบ prefix ที่ต้องร่วมทะเบียนกับเลข auto หรือไม่; ห้ามถือว่าเลขสูงสุดใน DB เป็นเลขสูงสุดของหน่วยงานหากมีสมุดทะเบียนภายนอก
- **ต้องตรวจข้อมูลจริง:** คำร้องรายคน/ไฟล์เก่าที่ active ซ้อนฉบับรวม, ไฟล์สูญหาย, หรือเลขซ้ำที่มีอยู่แล้วต้องได้รับการจัดหมวดก่อน migration

## นอกขอบเขต

- ระบบสร้าง DOCX/PDF จาก template ที่อัปโหลดใน `/staff/settings/documents` เป็นอีกงานหนึ่ง; แผนนี้ใช้ PDF generator ปัจจุบัน
- การรองรับนักศึกษาเกิน 6 คนต่อหนังสือหนึ่งฉบับ
- การแก้ประวัติเอกสารหรือ PDF ที่ออกแล้วโดยไม่สร้าง revision
- การเปลี่ยนข้อมูลบริษัท master หรือวันฝึกเป็นรายคนเมื่อยังไม่มีข้อมูลต้นทาง
