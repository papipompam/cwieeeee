# แผน UX/UI Flow: รอบสหกิจ

## เป้าหมาย

ทำให้เจ้าหน้าที่จัดการข้อมูลของแต่ละรอบสหกิจได้โดยไม่สับสนว่ากำลังทำงานอยู่ในรอบใด
และรองรับขอบเขตที่จะเพิ่มขึ้น เช่น การยืนยันคำร้อง การจัดอาจารย์นิเทศ ตารางนิเทศ
การประเมิน งบประมาณ และเอกสาร

หน้าที่เป็นรายการข้อมูลให้ใช้ **ตารางเป็นรูปแบบหลัก** เพราะเจ้าหน้าที่ต้องเปรียบเทียบ
ค้นหา กรอง และจัดการข้อมูลจำนวนมาก ส่วน card ใช้เฉพาะตัวเลขสรุปหรือ empty state
ที่ไม่เหมาะกับตาราง

## หลักการสำคัญ

- รอบสหกิจเป็น workspace context: ผู้ใช้เลือกรอบก่อน แล้วจึงทำงานภายในรอบนั้น
- sidebar หลักแสดงเพียง `รอบสหกิจ` ไม่เพิ่มทุกกระบวนการของรอบลง sidebar
- URL ทุกหน้าภายในรอบต้องมี `cycleId` เพื่อให้ refresh, bookmark และแชร์ URL ได้
- ชื่อรอบ รุ่น ช่วงฝึก และสถานะต้องปรากฏชัดบนทุกหน้าภายในรอบ
- ใช้ตารางสำหรับข้อมูลที่ต้องเปรียบเทียบหลายรายการ และใช้ summary card เท่าที่จำเป็น
- ไม่เพิ่มกราฟ หากตัวเลข สถานะ หรือตารางอธิบายข้อมูลได้ชัดกว่า
- รอบที่ปิดแล้วเป็น read-only เว้นแต่มีสิทธิ์หรือ flow เปิดรอบใหม่ที่กำหนดภายหลัง

## Flow หลัก

```text
Sidebar: รอบสหกิจ
        ↓
หน้ารายการรอบสหกิจ
        ↓ เลือก "เข้าสู่รอบ"
Workspace ของรอบ 2/2569 · รุ่น 2566
        ├── ภาพรวมรอบ
        ├── คำร้องนักศึกษา
        ├── การจัดสถานประกอบการ
        ├── อาจารย์นิเทศ
        ├── ตารางนิเทศ
        ├── การประเมิน
        ├── งบประมาณ
        └── เอกสาร
```

## 1. หน้ารายการรอบสหกิจ

Route: `/staff/cooperative-cycles`

### Header

- ชื่อหน้า: `รอบสหกิจ`
- Primary action: `เพิ่มรอบสหกิจ`
- ไม่เพิ่ม action อื่นใน header จนกว่าจะมีงานที่ใช้บ่อยจริง

### Filter bar

วางเหนือ table โดยใช้ `UDashboardToolbar` หรือพื้นที่ controls ของหน้า:

- ค้นหาจากภาคเรียน ปีการศึกษา หรือรุ่นนักศึกษา
- ตัวกรองสถานะ: ทั้งหมด, เปิดรับคำร้อง, ปิดรับคำร้อง, กำลังฝึกงาน, ปิดรอบ
- ปุ่ม refresh ใช้ `<UIButtonRefresh>`
- เรียงค่าเริ่มต้นจากปีการศึกษาและภาคเรียนล่าสุดก่อน

### ตารางรอบสหกิจ

ใช้ `UTable` โดยมีคอลัมน์เริ่มต้น:

| คอลัมน์ | ข้อมูล |
| --- | --- |
| รอบสหกิจ | เช่น `2/2569` และใช้เป็นลิงก์เข้าสู่รอบ |
| รุ่นนักศึกษา | เช่น `2566` |
| ช่วงฝึกงาน | วันเริ่มต้น–วันสิ้นสุด |
| สถานะ | `UBadge` พร้อมข้อความ ห้ามใช้สีอย่างเดียว |
| นักศึกษา | จำนวนที่อยู่ในรอบ เช่น `42 คน` |
| ความคืบหน้า | ข้อความสรุปสั้นตามสถานะของรอบ |
| จัดการ | เมนู `UDropdownMenu` สำหรับเข้าสู่รอบ แก้ไข และปิดรอบ |

แนวทางการแสดงผล:

- คลิกชื่อรอบหรือ action `เข้าสู่รอบ` เพื่อเปิด workspace
- ไม่ทำให้ทั้งแถวคลิกได้ เพื่อหลีกเลี่ยงการชนกับ action ในแถว
- action หลักที่ใช้บ่อยให้มองเห็นได้ ส่วน action รองรวมในเมนู `•••`
- การลบหรือปิดรอบต้องใช้ `<UIConfirmModal>` และระบุชื่อรอบในข้อความยืนยัน
- รอบที่มีข้อมูลอ้างอิงแล้วไม่ควรลบ ให้ปิดรอบแทน

## 2. Workspace ของรอบ

Route หลัก: `/staff/cooperative-cycles/:cycleId`

### Context header

แสดงข้อมูลเดิมบนทุกหน้าภายในรอบ:

```text
รอบสหกิจ / 2/2569

2/2569 · นักศึกษารุ่น 2566                    [กำลังฝึกงาน]
1 พ.ย. 2569 – 28 ก.พ. 2570             [เปลี่ยนรอบ ▾]
```

- ใช้ `UDashboardNavbar` สำหรับชื่อหน้าปัจจุบัน
- แสดงชื่อรอบ รุ่น ช่วงฝึก และสถานะโดยไม่ต้องเปิดหน้ารายละเอียด
- `เปลี่ยนรอบ` ใช้ `USelectMenu` เมื่อมีหลายรอบและต้องค้นหาได้
- การเปลี่ยนรอบต้องพาไปหน้าเดียวกันของรอบใหม่เมื่อ route นั้นรองรับ
- หากรอบถูกปิด ให้แสดง `UAlert` ว่าข้อมูลเป็น read-only

### Navigation ภายในรอบ

Desktop ใช้ route-based `UNavigationMenu` ใน `UDashboardToolbar`:

| เมนู | Route ต่อท้าย | Icon |

| ภาพรวม | `/` | `i-lucide-layout-dashboard` |

| สถานประกอบการ | `/placements` | `i-lucide-building-2` |
| อาจารย์นิเทศ | `/supervisors` | `i-lucide-users-round` |
| ตารางนิเทศ | `/visits` | `i-lucide-calendar-days` |
| การประเมิน | `/evaluations` | `i-lucide-clipboard-check` |
| งบประมาณ | `/budgets` | `i-lucide-wallet-cards` |
| เอกสาร | `/documents` | `i-lucide-files` |

Mobile ใช้ `USelectMenu` หรือ navigation drawer แทนการบีบเมนูทั้งหมดไว้ในบรรทัดเดียว

เมื่อจำนวนเมนูมากขึ้น ค่อยแบ่งเป็นกลุ่ม `การรับเข้ารอบ`, `การนิเทศ` และ `การบริหาร`
โดยไม่ซ้อนเมนูเกิน 1 ระดับ

## 3. หน้าภาพรวมรอบ

Route: `/staff/cooperative-cycles/:cycleId`

หน้า overview ใช้ข้อมูลสรุปเพื่อชี้งานที่ยังต้องทำ ไม่ใช่ dashboard ที่เต็มไปด้วยกราฟ

### Summary

ใช้ card ขนาดเล็กเฉพาะตัวเลขสรุป:

- นักศึกษาในรอบ
- คำร้องรอตรวจสอบ
- นักศึกษาที่ยังไม่มีอาจารย์นิเทศ
- การนิเทศที่ยังไม่กำหนดวัน
- แบบประเมินที่ยังไม่ครบ
- งบประมาณที่รอจัดสรร

ใช้ตารางเป็นส่วนหลักของหน้า:

## 4. Pattern ของหน้ารายการภายในรอบ

ทุกโมดูลภายในรอบใช้ pattern เดียวกันเพื่อลดการเรียนรู้ใหม่:

```text
Context header ของรอบ
Navigation ภายในรอบ
ชื่อหน้า + primary action
Search / filters / refresh
Table
Pagination
```

มาตรฐานร่วมของ table:

- ใช้ `UTable`
- คอลัมน์แรกเป็นข้อมูลหลักที่ระบุตัว record ได้
- สถานะใช้ `UBadge` พร้อมข้อความ
- คอลัมน์สุดท้ายเป็น action
- filter อยู่เหนือ table ไม่ซ่อนใน modal
- แยก empty state ออกจาก no-results state
- loading ใช้ skeleton ตามโครง table
- error แสดง `UAlert` พร้อมปุ่มลองใหม่
- pagination แสดงเมื่อข้อมูลมากกว่าหนึ่งหน้า ไม่แสดง control ที่ยังไม่มีผล
- bulk action เพิ่มเฉพาะ flow ที่มีการทำงานหลายรายการจริง เช่น อนุมัติคำร้องหลายคน
- action ที่ส่งข้อมูลใช้ loading state และป้องกันการกดซ้ำ

## 6. Route structure

```text
/staff/cooperative-cycles
/staff/cooperative-cycles/:cycleId
/staff/cooperative-cycles/:cycleId/applications
/staff/cooperative-cycles/:cycleId/placements
/staff/cooperative-cycles/:cycleId/supervisors
/staff/cooperative-cycles/:cycleId/visits
/staff/cooperative-cycles/:cycleId/evaluations
/staff/cooperative-cycles/:cycleId/budgets
/staff/cooperative-cycles/:cycleId/documents
```

ทุก API mutation ต้องตรวจว่า record เป็นของ `cycleId` ที่กำลังทำงานจริง การซ่อนข้อมูล
ใน frontend ไม่เพียงพอสำหรับการแยกสิทธิ์หรือป้องกันการแก้ข้อมูลข้ามรอบ

## 7. การป้องกันการทำงานผิดรอบ

- แสดงชื่อรอบใน header ของทุกหน้า
- primary action ระบุ context เมื่อมีความเสี่ยง เช่น `เพิ่มการนิเทศในรอบ 2/2569`
- confirmation ที่มีผลสำคัญต้องระบุชื่อรอบและรายการที่ได้รับผลกระทบ
- เมื่อเปลี่ยนรอบ ให้คงโมดูลเดิมถ้ามี และกลับ overview หาก route นั้นใช้ไม่ได้
- ไม่อาศัย “รอบล่าสุด” หรือค่าจาก browser เป็น source of truth เพียงอย่างเดียว
- รอบปิดแล้วซ่อน action แก้ไขและแสดงเหตุผล ไม่ปล่อยปุ่ม disabled โดยไม่มีคำอธิบาย
- toast ใช้แจ้งผลของ action ผ่าน `useNotify()`; validation ต้องอยู่ใกล้ field/section

## 8. ลำดับการพัฒนา

1. ทำหน้ารายการรอบสหกิจแบบ table พร้อม search, status filter และ action
2. ทำ context header และ navigation ภายในรอบ
3. ทำ overview ด้วย summary ที่จำเป็นและตารางงานคงเหลือ
4. ทำโมดูลคำร้องเป็น vertical slice แรกเพื่อพิสูจน์ table/filter/action pattern
5. reuse pattern กับสถานประกอบการ อาจารย์นิเทศ และตารางนิเทศ
6. ออกแบบการประเมิน งบประมาณ และเอกสารเมื่อ business rules ชัดเจน

## 9. เกณฑ์ยอมรับ

- ผู้ใช้มองเห็นได้ทันทีว่ากำลังทำงานในรอบใด
- ข้อมูลรายการหลักแสดงเป็นตารางและค้นหา/กรองได้
- เปิด URL โดยตรงหรือ refresh แล้วยังคงอยู่ในรอบและโมดูลเดิม
- active navigation ถูกต้องทั้ง sidebar หลักและเมนูภายในรอบ
- mobile สามารถเปลี่ยนโมดูลได้โดยเมนูไม่ล้นหน้าจอ
- รอบที่ปิดแล้วไม่สามารถแก้ข้อมูลผ่าน UI หรือ API ปกติ
- loading, empty, no-results และ error states แยกจากกันชัดเจน
- ใช้ Nuxt UI, semantic colors จาก `app/app.config.ts` และ Lucide icons ที่มีอยู่
- ไม่มี dependency, global store หรือ abstraction ใหม่โดยยังไม่มีความจำเป็น
- `pnpm typecheck` และ `pnpm build` ผ่านหลัง implementation

## นอกขอบเขตของแผนนี้

- notification center และระบบแจ้งเตือนอัตโนมัติ
- dashboard analytics และกราฟแนวโน้ม
