# แผนพัฒนาระบบส่วนเจ้าหน้าที่ระยะแรก

## เป้าหมาย

สร้างข้อมูลตั้งต้นที่เจ้าหน้าที่ต้องใช้ก่อนเริ่มกระบวนการคำร้องและการนิเทศสหกิจศึกษา ได้แก่ รอบสหกิจ นักศึกษา อาจารย์ และสถานประกอบการ โดยทำแต่ละส่วนให้ใช้งานจริงครบตั้งแต่หน้าจอ API จนถึงฐานข้อมูล

แผนนี้ยังไม่รวมระบบเข้าสู่ระบบ การยื่นคำร้อง การเลือกสถานประกอบการ การจัดอาจารย์นิเทศ เอกสารราชการ และผลการนิเทศ

## หลักการร่วม

- ใช้ Nuxt 4, Nuxt UI, Prisma และ PostgreSQL ตามโครงสร้างปัจจุบัน
- ใช้ semantic colors และ UI primitives ที่กำหนดไว้ใน `AGENTS.md` และ `app/app.config.ts`
- แบบฟอร์มต้องแสดง validation ใกล้ช่องข้อมูล และใช้ toast แจ้งผลระดับ action
- รายการทุกหน้าต้องค้นหา กรอง และรองรับสถานะว่าง กำลังโหลด และเกิดข้อผิดพลาด
- ยืนยันก่อนลบด้วย `UIConfirmModal`
- ลบได้เมื่อข้อมูลยังไม่ถูกอ้างอิง หากถูกใช้งานแล้วให้ปฏิเสธการลบและแนะนำให้เปลี่ยนสถานะเป็นไม่ใช้งานหรือปิดรอบ
- ยังไม่สร้าง abstraction กลางหรือเพิ่ม dependency จนกว่าจะมีการใช้งานซ้ำจริง

## 1. รอบสหกิจ

### ข้อมูล

- ภาคเรียน เป็นจำนวนเต็ม เช่น `2`
- ปีการศึกษา พ.ศ. เช่น `2569`
- รุ่นนักศึกษา พ.ศ. เช่น `2566`
- วันเปิดรับคำร้อง
- วันปิดรับคำร้อง
- วันเริ่มฝึก
- วันสิ้นสุดฝึก
- สถานะ:
  - เปิดรับคำร้อง
  - ปิดรับคำร้อง
  - กำลังฝึกงาน
  - ปิดรอบ
- หมายเหตุ ไม่บังคับ

ไม่ใช้สถานะ `ร่าง` เพื่อลดขั้นตอน เมื่อสร้างรอบใหม่ให้สถานะเริ่มต้นเป็น `เปิดรับคำร้อง` และเจ้าหน้าที่เปลี่ยนสถานะได้จากฟอร์มแก้ไขเดิม ไม่ต้องมี workflow อนุมัติเพิ่ม

ชื่อที่แสดงให้ประกอบจากข้อมูล เช่น `ภาคเรียนที่ 2/2569 รุ่น 2566` โดยไม่เก็บชื่อซ้ำในฐานข้อมูล

### กฎข้อมูล

- วันเปิดรับคำร้องต้องไม่เกินวันปิดรับคำร้อง
- วันเริ่มฝึกต้องไม่เกินวันสิ้นสุดฝึก
- ภาคเรียน ปีการศึกษา และรุ่นต้องเป็นจำนวนเต็มบวก
- ไม่อนุญาตให้มีรอบที่ภาคเรียน ปีการศึกษา และรุ่นซ้ำกัน
- รอบที่มีคำร้องหรือรายการฝึกงานแล้วห้ามลบ

### หน้าจอ

- `/staff/cooperative-cycles` รายการ ค้นหา กรองสถานะ เพิ่ม แก้ไข และลบ
- ใช้ modal หรือ slideover สำหรับฟอร์มได้ถ้าข้อมูลยังพอดีในหน้าจอ ไม่สร้างหน้ารายละเอียดจนกว่าจะมีข้อมูลที่ต้องแสดงจริง

## 2. นักศึกษาและอาจารย์

### นักศึกษา

- รหัสนักศึกษา เป็นข้อความและไม่ซ้ำ
- คำนำหน้า
- ชื่อ
- นามสกุล
- เพศ
- รุ่น พ.ศ. เช่น `2566`
- หมู่เรียน เป็นจำนวนเต็มบวก เช่น `1`, `2`, `4`
- สถานะใช้งาน

รุ่นและหมู่เรียนเก็บในรายการนักศึกษาโดยตรงก่อน ยังไม่สร้างตารางรุ่นหรือห้องเรียน เพราะขณะนี้ไม่มีข้อมูลอื่นของรุ่นและห้องที่ต้องจัดการแยก

### อาจารย์

- รหัสอาจารย์ เป็นข้อความและไม่ซ้ำ
- คำนำหน้า
- ชื่อ
- นามสกุล
- เพศ
- เบอร์มือถือ
- สถานะใช้งาน

### กฎข้อมูล

- คำนำหน้าไม่อนุมานจากเพศ
- เบอร์มือถือเก็บเป็นข้อความเพื่อรักษาเลขศูนย์นำหน้า
- รายการที่เคยถูกอ้างอิงในกระบวนการสหกิจห้ามลบ ให้เปลี่ยนเป็นไม่ใช้งานแทน

### หน้าจอ

- `/staff/students` ค้นหาด้วยรหัสหรือชื่อ และกรองรุ่น หมู่ และสถานะ
- `/staff/teachers` ค้นหาด้วยรหัสหรือชื่อ และกรองสถานะ
- ทำ CRUD นักศึกษาให้เสร็จก่อน แล้วจึงนำรูปแบบหน้ารายการและฟอร์มที่พิสูจน์แล้วไปใช้กับอาจารย์

## 3. สถานประกอบการ

### ข้อมูล

- ชื่อสถานประกอบการ
- ชื่อบุคลากรผู้ติดต่อหลักหนึ่งคน
- เบอร์โทรศัพท์ ไม่บังคับ
- อีเมล ไม่บังคับ
- บ้านเลขที่/อาคาร
- หมู่ ไม่บังคับ
- ซอย ไม่บังคับ
- ถนน ไม่บังคับ
- ตำบล/แขวง
- อำเภอ/เขต
- จังหวัด
- รหัสไปรษณีย์
- ละติจูด ไม่บังคับ
- ลองจิจูด ไม่บังคับ
- หมายเหตุการเดินทาง ไม่บังคับ
- สถานะใช้งาน

ไม่เก็บเลขประจำตัวผู้เสียภาษี และยังไม่สร้างตารางบุคลากรแยก

### ความยืดหยุ่นของชื่อบุคลากร

ชื่อบุคลากรในสถานประกอบการเป็นเพียงค่าเริ่มต้นสำหรับการติดต่อหรือออกเอกสารครั้งใหม่ เมื่อสร้างรายการฝึกงานหรือเอกสารในอนาคต ให้คัดลอกชื่อนี้ไปเก็บในรายการนั้นและเปิดให้เจ้าหน้าที่แก้ชื่อเฉพาะครั้งได้

วิธีนี้ทำให้:

- ฟอร์มสถานประกอบการยังกรอกบุคลากรเพียงคนเดียว
- เปลี่ยนผู้ติดต่อหลักของบริษัทได้ง่าย
- เอกสารเก่ายังคงชื่อบุคคลเดิม ไม่เปลี่ยนตามข้อมูลบริษัท
- ไม่ต้องสร้างระบบจัดการบุคลากรหลายคนก่อนมีความจำเป็น

### ที่อยู่และแผนที่

- เก็บที่อยู่แบบแยกช่องและเก็บพิกัดเป็น `latitude` กับ `longitude`
- จังหวัดเลือกจากรายการ ส่วนภูมิภาคให้คำนวณจากจังหวัดเพื่อป้องกันข้อมูลขัดกัน
- ระยะแรกสามารถกรอกที่อยู่และพิกัดได้โดยยังไม่ผูกผู้ให้บริการแผนที่
- ขั้นเพิ่มแผนที่ต้องรองรับค้นหาสถานที่ คลิกปักหมุด ลากหมุด และแสดงตำแหน่งเดิมเมื่อแก้ไข
- เลือกผู้ให้บริการแผนที่หลังประเมิน API key ค่าใช้จ่าย การค้นหาที่อยู่ภาษาไทย และเงื่อนไขการใช้งาน

### หน้าจอ

- `/staff/companies` ค้นหาด้วยชื่อ กรองจังหวัด ภูมิภาค และสถานะ
- `/staff/companies/new` และ `/staff/companies/[id]` ใช้หน้าฟอร์มเต็ม เพราะข้อมูลที่อยู่และแผนที่มีหลายช่อง

## โครงสร้างข้อมูลเบื้องต้น

แก้ model `Student` เดิมและเพิ่ม model ต่อไปนี้:

- `CooperativeCycle`
- `Student`
- `Teacher`
- `Company`

ยังไม่เพิ่มตารางเชื่อมระหว่างนักศึกษากับรอบสหกิจ ตารางคำร้อง หรือข้อมูลเอกสารจนกว่าจะเริ่ม feature นั้น ส่วนชื่อบุคลากรเฉพาะรายการจะเพิ่มพร้อม model รายการฝึกงานหรือเอกสาร เพื่อไม่สร้าง field ที่ยังไม่มีผู้ใช้

## ลำดับดำเนินงาน

### ระยะ A: รอบสหกิจ

1. ออกแบบ Prisma model, enum สถานะ และ migration
2. ทำ API รายการ เพิ่ม แก้ไข และลบ พร้อม validation
3. ทำหน้ารายการและฟอร์ม
4. ตรวจ CRUD, validation, unique constraint และกรณีลบไม่ได้

### ระยะ B: นักศึกษา

1. ขยาย `Student` model และสร้าง migration
2. ทำ API และหน้า CRUD พร้อมตัวกรองรุ่นและหมู่
3. ตรวจรหัสซ้ำ การค้นหา และการเปลี่ยนสถานะใช้งาน

### ระยะ C: อาจารย์

1. เพิ่ม `Teacher` model และ migration
2. ใช้รูปแบบ CRUD ที่ผ่านการใช้งานจากนักศึกษา
3. ตรวจรหัสซ้ำ เบอร์มือถือ และสถานะใช้งาน

### ระยะ D: สถานประกอบการ

1. เพิ่ม `Company` model และ migration
2. ทำ API และหน้าฟอร์มข้อมูลบริษัท ที่อยู่ และผู้ติดต่อหลัก
3. เพิ่มการเลือกจังหวัดและคำนวณภูมิภาค
4. ตรวจค้นหา ตัวกรอง และความถูกต้องของที่อยู่

### ระยะ E: แผนที่

1. เลือกผู้ให้บริการจากข้อจำกัดจริงของโครงการ
2. เพิ่มแผนที่ในฟอร์มเดิมโดยไม่เปลี่ยนโครงสร้างที่อยู่
3. ตรวจการค้นหา ปักหมุด แก้ตำแหน่ง และเปิดข้อมูลเดิม

## การตรวจรับแต่ละระยะ

- `pnpm typecheck` ผ่าน
- `pnpm build` ผ่านเมื่อจบหนึ่งโมดูล
- `pnpm exec prisma validate` ผ่านหลังแก้ schema
- migration ใช้กับฐานข้อมูลว่างได้
- ทดสอบ flow เพิ่ม ดู แก้ไข ลบหรือปฏิเสธการลบ และ validation ที่สำคัญ
- UI ใช้งานได้ทั้งจอมือถือและเดสก์ท็อป รวมถึงใช้งานด้วยแป้นพิมพ์
- final diff ไม่มี dependency หรือ abstraction ที่ยังไม่ถูกใช้งาน

## ขั้นถัดไปหลังจบแผนนี้

ออกแบบระบบคำร้องเข้าร่วมรอบสหกิจ ซึ่งจะเป็นจุดเชื่อม `Student`, `CooperativeCycle`, `Company` และข้อมูลชื่อผู้รับเอกสารเฉพาะครั้ง ก่อนต่อยอดไปยังการอนุมัติ การจัดอาจารย์นิเทศ และเอกสารส่งตัว
